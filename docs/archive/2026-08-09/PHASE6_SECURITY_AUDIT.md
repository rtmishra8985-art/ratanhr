## 1. AUTHENTICATION

### 1.1 Login Flow
**File:** `HRMS.Infrastructure/Services/AuthService.cs`

| Mechanism | Implementation | Finding |
|---|---|---|
| Password verification | `BCrypt.Net.BCrypt.Verify(dto.Password, user.PasswordHash)` | ✅ Constant-time BCrypt |
| Unknown account response | Same error message for missing user and wrong password | ✅ No account enumeration |
| Portal scoping | `dto.Portal` must match `user.Role` exactly | ✅ Admin cannot login via Employee portal |
| Soft-deleted accounts | `u.IsActive && !u.IsDeleted` condition on lookup | ✅ Deleted accounts blocked |
| MFA step-up | MFA-enabled accounts receive `TempToken` only; full JWT requires TOTP verification | ✅ No MFA bypass on login |

### 1.2 Account Lockout
**File:** `HRMS.Infrastructure/Services/AuthService.cs` lines 20–22, 60–95

```
MaxFailedAttempts = 5
LockoutDuration   = 15 minutes
```

- After 5 consecutive wrong passwords, `LockoutUntil = DateTime.UtcNow + 15 min` is persisted.
- The counter resets on successful login.
- A locked account returns `"Account temporarily locked"` even with the correct password during the lockout window.
- **TC-S05, TC-S06, TC-S07 verify this behaviour.**

### 1.3 Password Reset
- Tokens are 32-byte cryptographically random values (`RandomNumberGenerator.GetBytes(32)`).
- Stored as SHA-256 hash — raw token is only ever sent via email.
- Single-use: `_db.PasswordResetTokens.Remove(resetToken)` after successful use.
- Expires after 30 minutes.
- On password reset, **all active refresh tokens are revoked** (session invalidation).
- Reset link is only logged in Development (`_env.IsDevelopment()` gate) — never in production.

### 1.4 Password Change
- Requires current password verification before accepting new password.
- All active refresh tokens are revoked immediately on change.
- `MustChangePassword` is cleared.

## 2. JWT SECURITY

### 2.1 Algorithm
**File:** `HRMS.Infrastructure/JWT/JwtService.cs`

| Property | Value | Finding |
|---|---|---|
| Algorithm | `RS256` (RSA-SHA256 asymmetric) | ✅ Not HS256 |
| Key size | RSA-2048 (generated by `scripts/generate-rsa-keys.sh`) | ✅ |
| Signing key | Private PEM — server only; never in config files | ✅ |
| Validation key | Public PEM — safe to share | ✅ |
| Access token expiry | 30 minutes (configurable `Jwt:ExpiresInMinutes`) | ✅ Reduced from prior 8–12 h |
| RSA key caching | `Lazy<RsaSecurityKey>` singletons — one RSA.Create() per app lifetime | ✅ No memory leak |

**TC-S08** verifies `parsed.Header.Alg == SecurityAlgorithms.RsaSha256`.  
**TC-S09** verifies token expiry ≤ 31 minutes.

### 2.2 Claims
JWT payload contains:
- `sub` (NameIdentifier = userId)
- `role` (admin / employee / superadmin)
- `companyId` (tenant scope — absent for SuperAdmin)
- `adminRole` (fine-grained admin permission)
- `mustChangePassword`
- `employeeId` (employee code, for Employee-role tokens only)

**TC-S10** verifies all required claims are present for an employee-role token.

### 2.3 MFA Temp Token
- Short-lived: 5 minutes, `mfa_pending=true` claim.
- `ValidateTempToken` rejects tokens without the `mfa_pending` claim — a full access JWT cannot be used as a temp token.
- **TC-S11, TC-S12, TC-S13** cover temp token lifecycle.

### 2.4 Cookie Security
**File:** `HRMS.API/Controllers/BaseController.cs`

| Cookie | HttpOnly | Secure | SameSite | Path |
|---|---|---|---|---|
| `hrms_access_token` | `true` | `true` | `Strict` | `/` |
| `hrms_refresh_token` | `true` | `true` | `Strict` | `/api/auth/refresh` |

Access token is never returned in the response body — it is set as an HttpOnly cookie.  
Refresh token is path-scoped to prevent it from being sent to any endpoint other than `/api/auth/refresh`.  
**TC-S14** and **TC-S15** pin these values.

## 5. RATE LIMITING

**File:** `HRMS.API/Program.cs` lines 315–369

| Policy | Limit | Window | Backend |
|---|---|---|---|
| `login` | 10 req | 60 seconds | Redis (distributed) or in-memory |
| `sensitive` | 5 req | 60 seconds | Redis (distributed) or in-memory |
| `api` | 120 req | 60 seconds | Redis (distributed) or in-memory |

- `Retry-After` header is included on `429` responses.

## 16. MULTI-TENANT ISOLATION — Company A vs Company B

### 16.1 Architecture

The isolation is implemented at three layers:

#### Layer 1: EF Core Global Query Filters
**File:** `HRMS.Infrastructure/Data/ApplicationDbContext.cs`

All tenant-owned entity sets (Employee, Attendance, Payroll, Leave, SalaryStructure, Bonus, Deduction, Asset, Document, Notification, Recruitment, Performance, Timesheet, etc.) have `HasQueryFilter` applied:

```csharp
private bool _filterByTenant =>
    _tenant != null && !_tenant.IsSuperAdmin && _tenant.CompanyId.HasValue;

// Applied to every ICompanyOwned entity set:
builder.Entity<Employee>()
    .HasQueryFilter(e => !_filterByTenant || e.CompanyId == _tenantCompanyId);
```

This filter is **database-level** — it is appended to every LINQ query as a SQL `WHERE company_id = @p0`. It is impossible to accidentally forget this filter on a per-query basis.

#### Layer 2: GenericRepository ICompanyOwned Check
**File:** `HRMS.Infrastructure/Repositories/GenericRepository.cs`

`GetByIdAsync` applies an additional runtime check for `ICompanyOwned` entities:

```csharp
if (entity is ICompanyOwned owned && tenantCtx.CompanyId.HasValue)
    if (owned.CompanyId != tenantCtx.CompanyId.Value) return null;
```

This ensures that even if a query somehow leaked through Layer 1, the repository still returns null for a cross-tenant entity.

#### Layer 3: Tenant Context Middleware
**File:** `HRMS.API/Program.cs` lines 509–539

After `UseAuthentication`, a middleware extracts the `companyId` JWT claim and writes it to the scoped `ITenantContext`:

```csharp
if (!int.TryParse(ctx.User.FindFirst("companyId")?.Value, out var cid) || cid <= 0)
{
    ctx.Response.StatusCode = StatusCodes.Status403Forbidden;
    // returns immediately — no service call proceeds
}
tenantCtx.CompanyId = cid;
```

A non-SuperAdmin request without a valid `companyId` claim is rejected with `403` before reaching any controller.

#### Layer 4: BaseController Fail-Closed Sentinel
**File:** `HRMS.API/Controllers/BaseController.cs` lines 29–31

```csharp
protected int? CallerCompanyIdOrNull =>
    User.IsInRole(AppRoles.SuperAdmin) ? (int?)null
    : int.TryParse(User.FindFirst("companyId")?.Value, out int cid) ? cid : (int?)-1;
```

When a non-SuperAdmin token is missing the `companyId` claim, `CallerCompanyIdOrNull` returns `-1` (an impossible primary key), not `null` (which would mean SuperAdmin-unrestricted scope). All `WHERE company_id = -1` queries return empty results.

## 20. ADDITIONAL HARDENING FINDINGS

### 20.1 Superadmin Password Bootstrap
- On first boot, superadmin password is set from `SUPERADMIN_INITIAL_PASSWORD` env var or a cryptographically random 16-char generated value.
- The known compromised BCrypt hash (`$2a$10$N9qo8u...`) from old migrations is detected and force-reset on startup.
- `MustChangePassword=true` is set so the operator must change it on first login.
- The password is **never logged** (`Log.Warning` confirms "was not written to logs").

### 20.2 MustChangePassword Middleware
**File:** `HRMS.API/Middleware/MustChangePasswordMiddleware.cs`

All authenticated requests (except `/api/auth/change-password` and `/api/auth/logout`) return `403 MustChangePassword` when `user.MustChangePassword = true`. This prevents use of default seeded passwords.

### 20.3 Response Compression
`EnableForHttps = true` is intentional: JWT is in an HttpOnly cookie (not in response body), so BREACH/CRIME attacks are not applicable to the sensitive session credential.

### 20.4 Forwarded Headers
`UseForwardedHeaders` is the **first** middleware — before rate limiter, before CORS, before auth. This ensures rate limiting runs against the real client IP (not the nginx proxy IP), preventing rate limit bypass by routing to a different reverse proxy.

## 23. CONCLUSION

The RatanHR HRMS codebase demonstrates a robust, defence-in-depth security posture:

1. **Authentication** is hardened with BCrypt (work factor 12), 5-attempt lockout, MFA TOTP, session revocation on password change/reset, and no account enumeration.
2. **JWT** uses RS256 asymmetric signing with 30-minute access tokens, HttpOnly cookies, and a fail-closed MFA bypass prevention on refresh.
3. **Multi-tenant isolation** is enforced at four independent layers (EF global query filter, GenericRepository ownership check, tenant middleware, BaseController sentinel), making cross-company data access structurally impossible without superadmin credentials.
4. **IDOR** was tested across the core entity surfaces plus CRM / Sales — including SalesLead, SalesCustomer, and SalesMeeting — with no vulnerability found.
5. **Secrets** — zero hardcoded credentials in any committed file. All secrets are injected at runtime via environment variables, validated at startup.
6. **File upload** is protected by extension allow-list, magic-byte check, AV scan (ClamAV), server-generated filenames, and path traversal prevention.
7. **CSRF** is enforced globally via double-submit cookie pattern, covering both Authorization header and HttpOnly cookie authentication modes.
