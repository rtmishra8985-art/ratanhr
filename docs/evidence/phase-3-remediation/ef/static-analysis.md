# EF Core Model/Snapshot Drift — Static Analysis (no dotnet available)

Runtime commands could not be executed (see `ef-attempt.txt` in this folder for the
exact command and error). The findings below come from direct source inspection only
and are marked accordingly — they are NOT a substitute for running
`dotnet ef migrations has-pending-model-changes`.

## Inventory

- DbContext: `HRMS.Infrastructure/Data/ApplicationDbContext.cs` (1,777 lines, 81 `DbSet<T>` properties)
- Design-time factory: `HRMS.Infrastructure/Data/ApplicationDbContextFactory.cs` (present)
- Migrations directory: `HRMS.Infrastructure/Migrations/MySql/` — 17 migration files, timestamped
  `20260726000001` through `20260806000001`
- Snapshot: `HRMS.Infrastructure/Migrations/MySql/ApplicationDbContextModelSnapshot_MySql.cs`
  (1,307 lines, 81 `modelBuilder.Entity(...)` blocks — entity **count** matches the 81 DbSets)
- The unique-payslip migration IS present on disk:
  `20260806000001_AddUniquePayslipConstraint.cs` (creates `ux_payslips_employee_month_year`
  on `payslips(employee_id, month, year)`)

## Confirmed drift (source-level, high confidence)

Only 4 of the 17 migrations have a matching `.Designer.cs` file:
`20260726000001`, `20260728000004`, `20260802000001`, `20260805000001`.
The other 13 — including the payslip migration itself — have **no** Designer file.
A normal EF Core workflow (`dotnet ef migrations add`) always generates one Designer.cs
per migration; this pattern is consistent with the snapshot header's own comment:
"This file is maintained as the MySQL model metadata for the hand-authored migration."
i.e., the snapshot was edited by hand rather than regenerated by the EF tool.

Comparing the actual `Payslip` entity (`HRMS.Domain/Entities/Payroll/Payslip.cs`, ~20
mapped scalar properties: Month, Year, WorkingDays, DaysPresent, BasicPay, HRA, DA,
Conveyance, MedicalAllowance, OtherAllowances, GrossEarnings, PFEmployee, PFEmployer,
ESI, PT, TDS, OtherDeductions, TotalDeductions, NetPay, CreatedAt, Status, RowVersion)
against its snapshot block:

```
modelBuilder.Entity("HRMS.MySql.payslips", b =>
{
    b.Property<int>("id")...
    b.Property<string>("employee_id")...
    b.Property<int?>("company_id")...
    b.HasKey("id");
    b.ToTable("payslips");
});
```

The snapshot declares 3 of ~22 mapped columns for `payslips`, and does **not** declare
the `ux_payslips_employee_month_year` unique index that migration
`20260806000001_AddUniquePayslipConstraint` creates. This same sparse pattern repeats
across the other entity blocks in the snapshot (most blocks list only PK + 1-3 columns
rather than every mapped property).

**Conclusion (static, not a substitute for the CLI check):** the snapshot is materially
out of sync with both the DbContext model and the actual migration history. Running
`dotnet ef migrations has-pending-model-changes` on a dotnet-capable machine will almost
certainly report pending changes. This is the root cause named in the task brief.

## Why this was not hand-patched here

Per the task's own constraints, manually patching a hand-authored sparse snapshot is
explicitly discouraged in favor of regenerating it through the supported EF Core
workflow, and no migration should be fabricated blind. Both require the `dotnet ef`
CLI, which is unavailable in this sandbox (see `ef-attempt.txt`). Patching ~1,300 lines
of hand-maintained snapshot by hand, without the tool available to verify the result
compiles and matches the model, would itself introduce new unverified drift.
